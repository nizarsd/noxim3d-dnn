# Claude Code prompt — top-N-sinks DP (design-time variant)

## Context

Paper 1 showed ~82% of NoC bytes converge on a small set of aggregator sinks, and DP's gain
comes from routing those flows. Hypothesis: computing DP cost-to-go for only the top-N hot
sinks, with all other destinations falling back to bufferlevel (BL) selection, retains most of
DP's gain while shortening the DP cycle by roughly the destination-count ratio — improving
table freshness at zero hardware cost.

This is the **design-time** variant only: the sink set is fixed per workload/packing from an
offline ranking. The runtime self-nomination variant and any RL scoping are **out of scope**.

Two turns. Turn 1 is investigate-only. Do not proceed to Turn 2 in the same session.

---

## Turn 1 — investigate only, no code changes

Produce `docs/TOPN-DP-INVESTIGATION.md` answering the following, with file paths and line
numbers for every claim. If unverifiable from source, say so.

1. **DP relaxation structure.** How does the DP pass iterate over destinations? Is the
   per-destination cost-to-go computed independently, so a destination subset is a clean
   restriction, or is there shared state across destinations that a subset would break?
2. **DP cycle scaling.** What sets the DP cycle length (currently 648)? Does it scale with
   destination count, DPSIZE, node count, or a fixed iteration budget? Give the formula or the
   loop bounds.
3. **Table layout.** Where is `dir_tbl` (or equivalent) sized and indexed? What does restricting
   it to N destinations require — sparse index, remap, or nothing?
4. **Per-packet policy switch.** At routing time, how is the selection policy chosen? Is there
   a per-destination hook, or is selection global? What is the minimal change to route
   "destination in DP set → DP, else → BL"? Confirm both paths sit under the same turn model
   so mixing them stays deadlock-free.
5. **Sink identification.** How are aggregator sinks identified from the trace? Does an
   offline per-sink ejection-load ranking already exist (§28 ejection-bandwidth normalisation,
   or the hot-tier lists from the predictor campaign)? Name the file or script.
6. **Hot-tier sizes.** From existing data, how many sinks carry the bulk of ejection load per
   workload × packing? Report the count at 80% and 95% of ejection bytes for ResNet (8,2,4),
   VGG (8,4,2), DeiT (16,1,16). This sets the N sweep range.
7. **Double-buffering.** Is the `dir_tbl[2]` + atomic active-index fix implemented? If not,
   state it plainly. A shorter DP cycle means more frequent table writes and more torn-read
   exposure, so Turn 2 is gated on this.
8. **Regression targets.** Identify the transpose1 bit-identical regression and the current
   full-DP and BL reference runs for the three (workload, packing) points above at the knee
   density. Turn 2 must reproduce them.

End with: READY / BLOCKED (reason) for Turn 2.

---

## Turn 2 — implement, gated on Turn 1 = READY

1. Add `-dptopn <N> <sinkfile>` where `sinkfile` lists sink node IDs in descending ejection
   load (generated by the ranking script from Turn 1, Q5). N = 0 must behave as pure BL;
   N = all sinks must match the current full-DP path.
2. Regressions, in order, before any sweep:
   - transpose1 bit-identical to current HEAD with the flag absent.
   - `-dptopn 0` statistically identical to BL on the three reference points (same seeds).
   - `-dptopn <all>` statistically identical to full DP on the same points. If table
     ordering makes bit-identity impossible, report the delta and its cause.
3. Sweep N ∈ {1, 2, 4, 8, hot-tier-80%, hot-tier-95%, all} on the three reference points at
   the knee density, same seeds as the references, n = 30 minimum.
4. Report per point: mean delay, p99, **fraction of full-DP gain retained** (defined against
   the BL and full-DP references), and measured DP cycle length. One table, one figure: gain
   retained vs N with DP cycle length on a secondary axis.
5. Write results to `docs/TOPN-DP-RESULTS.md`. Do not alter defaults; flag absent = current
   behaviour.
